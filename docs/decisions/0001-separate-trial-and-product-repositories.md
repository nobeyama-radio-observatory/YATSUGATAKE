# 0001. 試行（study-rfsoc）と製品（YATSUGATAKE）のリポジトリを分ける

- 状態: 採用
- 決定日: 2026-10-08
- 根拠: study-rfsoc の README（構成の考え方）・proj021 の README（目的）

## 背景

仕様が固まり、配布する製品版の .bit を作る段階に入った。一方で、複数の bit をビルドした後に出る問題への対処など、試行錯誤はまだ残る。

study-rfsoc は試行ごとに `projNNN/` を作る実験ノートの形で、**各 proj は自己完結（再現性を DRY より優先）**にしている。共通部分を直しても過去の proj が壊れない。

## 決定

- **study-rfsoc は試行の場として続ける。** 結果が読めない試行（方式の比較・原因の切り分け・陽性対照）はそこで行う。失敗した proj も消さない
- **YATSUGATAKE を製品の正典にする。** 共通コア＋9 本の bit・リリース・仕様・性能評価を持つ
- **製品のコード・仕様を変える作業は YATSUGATAKE で行う**（複数の bit のビルドで見つかった問題の修正を含む）。issue → ブランチ → PR とし、回帰の結果を PR に付ける
- **試行の結果で仕様が変わるときは、YATSUGATAKE に ADR を 1 本足し、根拠として study-rfsoc の proj を指す**

## 理由

- 製品は 9 本の bit が共通コア（時刻・TP・流れとリング・specd）を持ち、**1 か所の修正を全 bit で回帰する形でないと保守できない**。これは study-rfsoc の「自己完結・再現性 > DRY」と正反対の規約で、1 つの履歴に混ぜられない
- 同じリポジトリに置くと、利用者が clone したときに proj001〜の試行が全部付いてくる。リリースのタグが何を指すかも曖昧になる
- 試行の記録が製品の履歴に入らないので、製品側の履歴は「何が変わったか」だけを読めばよくなる

## 見送った案

- **同じリポジトリの別フォルダ**: 上の 2 つの規約が 1 つの履歴に混ざる
- **「完成版」と「開発版」で分ける**: 製品の改修（複数 bit のビルド後の修正）をどちらに置くかが曖昧になる。分ける軸は完成度ではなく「試行か製品か」

## 影響

- 開発の進め方は [`CONTRIBUTING.md`](../../CONTRIBUTING.md)
- 公開前の確かめは両方のリポジトリで行う（[`../publishing.md`](../publishing.md)）
